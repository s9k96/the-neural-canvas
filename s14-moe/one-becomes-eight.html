One Becomes Eight

A transformer's feed-forward block holds most of its weights, and every token runs through all of them. A mixture of experts stores many smaller blocks and runs only the few a router picks. This page trains a dense model, turns its feed-forward block into eight experts without changing a single output, and keeps training. The loss keeps falling, from exactly where it was.

00What was actually run

The assignment: train a dense model, convert it into a mixture of experts, and show that it continues to train and reduce its loss. Model size and data were left open.

How to read the markers

The session's reference model has 30.5 billion parameters, and most of the session is about it. That one change lets the number of parameters grow while the work per token stays small. Capacity grows with the total parameters; cost per token grows with the active ones. It also creates three problems, each a part of this session: choosing (a router decides which few each token uses), balancing (left alone, the router favours a few experts and the rest never learn), and placing (experts live on different GPUs, so tokens travel). A fourth topic is growing one from a model that already works — which is what this assignment does.

The costs are real too. Memory follows the total; experts on different GPUs mean every token travels (DeepSeek-V3 reported about one unit of communication per unit of compute); Switch diverged with a 16-bit router; and ST-MoE found MoE models overfit small fine-tuning sets more easily.

02The reference model, and its two sizes computed

The session uses one model throughout: the published shape of Qwen3-30B-A3B — 48 layers, hidden size 2,048, 32 query heads sharing 4 key-value heads, and in every layer 128 experts of width 768, of which each token uses 8. Every row below is recomputed from that shape alone.

03The layer, and what an expert is computed

A mixture-of-experts layer keeps attention exactly as it is and replaces the feed-forward network with a router and a set of experts. With T the chosen set and gᵢ the router's weights, which add to one:

y = Σi∈T gᵢ · Eᵢ(x)        Eᵢ(x) = Wdown( SiLU(Wgate x) ⊙ Wup x )

An expert is a small SwiGLU network with no attention and no embeddings of its own; it cannot produce text by itself, and the router chooses again for every token in every layer. The reference model's own configuration shows what an expert is: its standard feed-forward width is 6,144, and 8 × 768 = 6,144. A token uses the width of one ordinary feed-forward network, assembled from 8 pieces chosen out of 128. Training never assigns a subject to an expert; any specialisation is whatever falls out of training the router and experts together.

Mixtral 8x7B is not 56B: attention and embeddings are shared, so it is 47B, of which about 45B (96%) sit in the experts. The reference model's experts hold 28.99B of 30.53B, 95%.

05The router computed

The router multiplies the token's vector by one matrix and gets a logit per expert. A score function turns the logits into scores, the top k are kept, and the kept scores are rescaled to add to one. This is §7's worked token: 8 experts, its logits fixed. Softmax scores compete and add to one; sigmoid scores each expert on its own. The bias toggle is §13's balancer: it changes which experts are chosen and never the weights.

Two practical details keep the router stable, and the model on this page uses both: it runs in 32-bit (Switch's base model diverged in 16-bit; casting only the router fixed it and still ran faster than full 32-bit, 1,390 vs 1,160 examples a second), and it starts small, at a tenth of the usual initial scale.

06Many small experts, and what they learn reference

Early models used a few large experts; current ones use many small ones. Splitting experts finer and choosing proportionally more keeps compute fixed and multiplies the ways a token's network can be assembled:

DeepSeekMoE also introduced the shared expert, used by every token, as one place for common knowledge: removing it from their 2B model raised Pile loss from 1.808 to 2.414. DeepSeek-V3 and Kimi K2 keep one; the reference model, gpt-oss and MiMo use none, and OLMoE found no benefit. This page's model has no shared expert.

What experts learn surprises most people: kinds of tokens, much more than subjects. ST-MoE found experts for punctuation, verbs, names and numbers, and "for" and "pour" reaching the same expert. In Mixtral, arXiv, biology and philosophy text route almost identically, while Python's self and code indentation always reach the same experts. A few experts matter enormously — three of 6,144 in the reference shape create its extreme activations, and removing them cuts GSM8K accuracy by 53% — while REAP removed half the experts of two large models for under 2% accuracy.

07The assignment, part one: a dense model, then eight experts measured

The dense model is a small decoder whose feed-forward block is one SwiGLU network. It is converted by sparse upcycling (§15 of the notes): every expert starts as a copy of that network, a new router picks 2 of 8 per token, and the two weights are rescaled to add to one.

The check that has to come first

"It continues to train" means nothing if the conversion itself moved the model: a falling loss afterwards could just be the MoE recovering from damage the conversion did. With identical experts the output cannot change — Σ gᵢ·E(x) = E(x)·Σ gᵢ = E(x) — so the converted model must score the same as the dense one, before any MoE training step:

The consequence nobody mentions

The same identity means that at the moment of conversion the router gets no gradient from the language loss at all. Every choice gives the same output, so no choice is better than another. The router can only start learning after the experts have drifted apart on the different tokens its random initial choices sent them.

08The assignment, part two: it keeps training measured

Four branches start from the same dense checkpoint and read the same next tokens in the same order, so the only difference between them is the model. The dense model keeps training too, as the control: a dense model also keeps reducing its loss on new tokens, so "the MoE's loss falls" alone would only show that nothing broke.

10Load imbalance and collapse measured

The router and experts train together, and that creates a loop: an expert chosen a little more often gets more updates, gets better, gets scored higher, and is chosen even more. A router left alone favours a few experts; the rest stop learning. The standard measure is the maximum violation, MaxVio = (max load − mean load) / mean load: 0 is perfectly even, 1 means the busiest expert has twice the average. 11Capacity and dropped tokens computed from measured loads

The first fix limited how many tokens each expert could take per batch: capacity = tokens × k / experts × capacity factor. A token that arrives after its expert is full is dropped — it skips that expert and continues through the residual connection. For the reference model one 8,192-token sequence averages 512 tokens per expert, so a factor of 1.25 gives 640 slots.

The model on this page is dropless, like DeepSeek-V3, OLMoE and the reference model. But its measured loads say what a capacity limit would have cost: the slider applies a capacity factor to each branch's real per-step expert loads (the last 25 steps, every layer) and counts the overflow.

Switch used factors of 1.0 and 1.25 and dropped under 1%. MegaBlocks then made experts of any load run in one pass, and its dropless model reduced validation loss by 0.26 where capacity factor 1.0 managed 0.15. The overflow here is computed from 25-step totals, so it understates per-step peaks.

12Auxiliary loss vs the bias measured

The auxiliary loss (Switch) adds α·N·Σ fᵢ·Pᵢ to the training loss — fᵢ the fraction of tokens sent to expert i (no gradient: top-k is a step), Pᵢ its mean router probability (has one). It is when perfectly even and when collapsed onto one of 128. Its drawback: its gradient flows into the same router weights the language loss trains.

The bias (Wang et al., 2024) adds nothing to the loss. Every expert has a number added to its score only when choosing; after each step it moves by γ·sign(mean load − loadᵢ). Busy experts get pushed down, idle ones up, and the language-loss gradient is untouched — the notebook checks that the bias has no gradient and that the weights still come from the raw scores.

The ST-MoE router z-loss, (log Σ e^z)² averaged over tokens, penalises large logits for stability and was not needed at this scale.

13Balancing scope reference

Every balancing method counts load over some group of tokens: one sequence, one micro-batch on one GPU, or the whole batch across all GPUs. Balancing over a small group forces every group to use every expert, which blocks experts from specialising by subject. A micro-batch of only code would have to use the maths experts too.

14Growing again: clone families measured

Upcycling is a family of methods. Copy (sparse upcycling, what §07 did) makes every expert the whole network; partition gives each a slice; drop-upcycling copies and redraws a fraction of each copy's neurons. The hard part is always the same: making the copies become different.

The notes record a failure the published studies do not. The Lightning LM team grew 20 experts to 460 by cloning each 23 times without redrawing any neurons, with hard top-k, and dead experts rose 27 → 38 → 122 → 154 → 168 within a few hundred steps: the router could not tell near-identical clones apart, and each family collapsed onto a few members. Their fix was probabilistic selection during an early window. The same experiment, at this page's scale: the trained 8-expert model is grown to 32 experts (each cloned 4×), router columns tiled with 1% noise, top-k 2 → 4, and trained three ways on the same next tokens.

Upcycling saves compute only up to a point: a from-scratch MoE caught up after about 120% of the dense budget in the original study and 25% in OLMoE's. Skywork's rule is to train from scratch once the MoE budget passes twice the dense model's cost.

15Expert parallelism computed

The reference model's experts hold 28.99B parameters, far more than one GPU should train. Expert parallelism places different experts on different GPUs: at EP = 8, GPU g holds experts 16g to 16g+15 of every layer. Attention and the router run at home; each token is sent to the GPUs holding its 8 experts (dispatch, an all-to-all), computed there, and sent back (combine) — two all-to-alls each way, every MoE layer.

token "the" on GPU 2 picks experts 3, 17, 40, 41, 77, 90, 101, 126
fixed map e ÷ 16:  3→GPU0  17→GPU1  40→GPU2  41→GPU2  77→GPU4  90→GPU5  101→GPU6  126→GPU7
(40 and 41 are at home, so those two copies never leave)
count → exchange counts → dispatch → 16 experts run per GPU → combine → unpermute, weighted sum

Each token sends k copies of its vector: 8 × 2,048 × 2 bytes for dispatch and the same for combine, 7/8 of it off the GPU, × 48 layers × 2 for the backward pass. Megatron-LM's guideline follows from the network-card row: keep expert parallelism inside one node. DeepEP measured 726 GB/s inside a B200 node and about 90 GB/s across two.

16Expert parallelism with the other forms, and choosing a layout computed

A mixture-of-experts model has two kinds of weights, divided differently. Attention, router and embeddings are copied on every GPU, their gradients summed across all of them, and their optimizer state divided by ZeRO-1. Experts are already divided by expert parallelism; when there are more GPUs than the EP degree, each expert's copies sum gradients within their own smaller expert data-parallel group.

Activations at 34 bytes per token per hidden unit per layer. Megatron-LM publishes exactly the first row for this shape: EP 8, no tensor or pipeline parallelism, recomputing the expert activation and the layer norm. MoE Parallel Folding lets attention use tensor parallelism while experts use EP on the same cards (Mixtral 8x22B on 128 H100s: 46.3% → 49.3% utilisation); DualPipe overlaps one micro-batch's all-to-all with another's compute; EPLB re-places extra copies of the busiest experts when serving.

The nine steps, in order

Count total and active size → EP = GPUs per node → ZeRO-1 for the dense parts → check training state per GPU → add activations (recompute some if needed) → check tokens per expert (a few hundred or more; here ) → compare all-to-all with compute → cross nodes only when it does not fit → measure the step time and let the measurement choose.
