The Redundancy Tax

Eight GPUs running data parallelism hold 3,576 GiB of memory to store 447 GiB of information. ZeRO is the arithmetic of getting that back, one class of duplicated state at a time — and every measured number on this page came off 32 real processes talking over real sockets, not out of the formula it is being checked against.

00What was actually run

A graphics card holds a fixed amount of memory. The largest available hold 80 GB. The model this course is building has about 30 billion numbers in it, and every one has to be stored somewhere while it trains. This page is about what happens when the thing you are training is larger than the machine you are training it on, and it is written to be read on its own — from the arithmetic through to the decisions that follow from it.

The assignment asks for 32 virtual GPUs, a demo model on top of them, and a demonstration of how memory and computation change across ZeRO's stages. The word doing the most work there is simulate, and this submission takes a position on it: nothing measured here is simulated. The 32 GPUs are 32 operating-system processes in a gloo process group. Every byte reported as crossing the wire was handed to dist.isend and counted at that line.

How to read the markers

Parts of this session are arithmetic about hardware I do not have. The page never blurs the two. measured means it came out of a run on this machine. computed means it is arithmetic from the session's figures. reference means it is recorded from the course rather than derived here.

01Sixteen bytes for every weight computed

Start with the arithmetic, because it settles the question quickly. A weight is not one number. Training it means keeping four things, and they add to sixteen bytes.

The two running averages are the optimizer's memory: one tracks the average of recent gradients for that weight, the other the average of their squares. Both are 32-bit, four bytes each. The 32-bit copy of the weight exists because repeatedly adding very small updates to a 16-bit number loses them to rounding, so the authoritative value is kept at higher precision and a 16-bit version is made from it for the arithmetic. Section 06 measures that loss rather than asserting it.

Those dtypes are not a description of the model that ran — they are its dtypes. The engine holds bfloat16 parameters and gradients with a float32 master copy and float32 Adam moments, so the sixteen bytes below are bytes that were actually allocated.

03Data parallelism, and the two things it promises measured

The simplest way to use 32 GPUs is to give each a complete copy of the model and a different portion of the data. Each reads its own examples, runs them through its own copy, and produces its own gradients — and those gradients differ, because each GPU saw different text. The copies are then brought back into agreement: every GPU sends its gradients to every other, all of them compute the average, and each applies that same average to its own copy.

Averaging the gradients from 32 GPUs that each processed one sequence produces exactly the gradient a single GPU would have produced from all 32 at once. That is the property that lets a training recipe move from one GPU to many without changing what the model learns. It makes two promises, and both are checkable rather than assumable.

Promise one: the copies stay identical

They started identical and applied an identical update, so they must remain identical — with no drift, ever. This is what the whole arrangement rests on: the moment two ranks disagree about the weights, they are no longer training one model. Every rank hashes the entire model it can see, so the check is whether 32 hex strings are the same string.

Promise two: the global batch is a product, and only the product matters

Accumulation steps are repeats of the forward and backward pass before the weights move, used when the batch you want is larger than what fits at once.

If that formula is real, any factorization of the same global batch is the same training run. So the same 32 sequences were run two ways — and the second is exactly the configuration the previous production run used (section 18), which is why it was worth running rather than asserting.

04Three collectives, and the equivalence that makes ZeRO free

A collective is an operation every GPU performs together, at the same time, on data each of them holds a piece of. Three appear throughout this session, and the averaging step above is the first of them.

operationeach GPU starts witheach GPU ends with
all-reducea full set of valuesthe combined full set
reduce-scattera full set of valuesone slice of the combined set
all-gatherone slicethe full set

A reduce-scatter followed by an all-gather produces exactly what an all-reduce produces.

That sentence is the hinge of the whole session. It is why ZeRO-1 and ZeRO-2 are free: a ring all-reduce is implemented as precisely those two phases, so each GPU already sends about one copy of the data during the first and receives about one during the second — 2P in total. A stage that stops after the first phase and keeps the slice already in its hands has not added a single byte of traffic. It has simply declined to throw something away.

05The ring, one hop at a time

Worth watching rather than accepting. Each row is a GPU and each column is a chunk of the data. Every GPU starts holding its own version of all N chunks, and only ever sends to its right-hand neighbour. Step forward: during reduce-scatter the contributions accumulate until each GPU owns one complete chunk, and during all-gather those complete chunks travel back around until everyone has all of them. A number in a cell is how many of the N contributions it has collected; a filled cell has all N.

07What each ZeRO stage deletes

Look again at what data parallelism stores. Every GPU holds the full 16 bytes for every weight, and the copies are identical. Eight GPUs therefore hold eight identical copies of 447 GiB — 3,576 GiB of memory to store 447 GiB of information. Most of that is never needed in eight places: during the update each GPU applies the same average to the same weights and produces the same answer, so seven of the eight are repeating work already being done.

The idea is to give each GPU responsibility for one slice of the weights, let it keep only the state for that slice, and have it fetch anything else when it needs it. Every GPU receives a different slice, so all hold the same amount and none sits idle. That is ZeRO, for Zero Redundancy Optimizer, published by Microsoft in 2019 — an arrangement of storage, applied in three stages, each removing one more class of duplicated state.

08The ladder, measured measured

Four runs on 32 processes. Same model, same seed, same tokens in the same order. The only thing that changes is what each rank is allowed to keep. The measured column is not computed from the formula beside it — it is the sum of the byte sizes of the storages each rank actually held at the instant backward() returned.

Two numbers per stage, because the session's table has one

The ladder is the state a rank holds with no collective in flight, which is what the session's table describes. The peak is that plus the largest buffer a single collective needs. No implementation escapes the second, and the gap is wider here than it would be on a real model: the buffer is sized by the largest single tensor, and in a 2.6M-parameter model with a 2,048-token vocabulary the embedding is a far bigger share of the whole than it is at 30B. The gap is an artifact of the toy. The ladder is not.

09What it costs on the wire measured

The claim from section 04, now as a measurement: stages 1 and 2 cost nothing extra, and only stage 3 raises the bill. Stage 3 adds a gather of the weights on the way forward and another on the way back.

A correction the measurement forces

A ring collective does not move P. It moves P·(N−1)/N — each rank sends every chunk but its own, N−1 of the N. At 32 GPUs that is 0.969P, so data parallelism's real cost is 1.94P and ZeRO-3's is 2.91P. The session's 2P and 3P are the large-N limit of this, and at 32 GPUs the limit is 3% away. I would rather report 1.94P and explain it than report 2P and be quietly wrong.

10Is it still the same training run? measured

A memory saving that changed the answer would be worthless. Two claims, two different standards of proof.

Across the stages, the standard is bitwise. All four run the identical ring in the identical order on identical data; only the question of which rank keeps which slice differs. Every arithmetic operation therefore sees the same inputs in the same order, and the final weights must agree to the last bit. A tolerance here would be hiding something.

Against a single GPU, the standard is a tolerance — and its size is the finding

Section 03 says a distributed run is mathematically identical to a single-GPU run on a batch 32 times larger. Mathematically, yes. In floating point, no. One rank computing the gradient of 32 sequences in one matrix multiply, and 32 ranks computing one sequence each and summing around a bfloat16 ring, are different summation orders of the same quantity.

11Bucketing: the cost is paid per message, not per byte measured

Everything above reduces one tensor at a time: each of the model's parameter tensors gets its own ring, and a ring across 32 ranks is 31 hops in each direction. The session says gradients are instead collected into buckets, and that the bucket size sets a balance — smaller buckets start transferring earlier in the backward pass, larger ones pay the fixed cost of starting a transfer less often.

Rather than quote that, this run takes it to its limit: every gradient in the model packed into one buffer and reduced once. Both ends of the balance show up.

Which is also the argument for overlap

The backward pass runs from the last layer of the model to the first, so the gradients for the last layer are finished long before the pass reaches the first. Those gradients can begin their journey immediately, while the earlier layers are still being computed — a bucket is sent as soon as it fills, part way through the pass. That is the whole of overlapping communication with compute: communication that happens during computation costs nothing, and arranging it is a matter of configuration.

Smaller buckets give more room to overlap; larger ones amortise the fixed cost measured above. Production settings are a few hundred megabytes. There is a third effect that appears only on fast hardware: smaller buckets keep helping while the link drains them as fast as they arrive, but past that point the transfers queue behind each other and step time climbs again. ZeRO-3 needs the same treatment in the other direction — the weights for the next layer gathered while the current one is still computing. None of the overlap is implemented here, and given section 13's numbers it is the single change that would most improve this run.

13What this costs on hardware that is not a laptop computed

The useful question is not how slow my loopback is. It is: given a real interconnect and a real card, is the transfer small compared with the work? While a GPU is waiting for numbers to arrive, it is not computing.

The test is communication divided by compute. Below 1, a transfer that runs entirely during the computation is fully hidden. Move the controls: the card changes only the compute bar, the link changes only the network bar.

The least intuitive consequence of buying newer hardware

The volume does not move — 120 GB crosses the wire either way. What moves is the compute it has to hide behind, and a B200 step is less than half an H100 step. Faster GPUs raise the ratio of communication to compute, from 34% to 77% on the same InfiniBand link. Both are still below 1, so a fully overlapped transfer is still fully hidden — and that margin is the entire reason section 11's overlap stops being an optimization and becomes a requirement.

14The memory wall measured

The measured bytes-per-parameter, multiplied out to a real model. This is a ratio argument, and the assumption it rests on is worth stating: bytes-per-parameter is independent of parameter count for all four arrangements, which is exactly what makes the wall a function of world size alone. The four stages were re-run at 4, 8 and 16 GPUs to check that — the dots are measured, the lines extrapolate.

The floor that no GPU count reaches

Data parallelism and ZeRO-1 both leave the weight and the gradient — four bytes — replicated on every card at every world size. Four bytes across 30 billion weights is 111.8 GiB, and that figure is the same on one card as on a thousand. Four bytes fills a 74.5 GiB card exactly at 20 billion parameters. Drag the slider across that line and watch two of the four arrangements stop being available at any GPU count.

One thing these figures exclude: activations, the intermediate results the forward pass produces. Their size is set by the batch and the sequence length, and room has to be left for them, which pushes the practical threshold above what the table alone suggests. The common technique for controlling them is to discard them during the forward pass and recompute them during the backward pass, at a cost of roughly 30% more compute.

15Offload, and the trade it actually makes computed

A GPU is not the only memory in the machine. A node has system memory, usually far more than the GPUs have, and solid-state storage beyond that. State that is needed rarely can live in those slower places and be brought in when required.

The optimizer state is the natural candidate: twelve of the sixteen bytes, and touched exactly once per step. There are two versions. The simpler one parks the state in system memory and copies it to the GPU for the update. The more effective one performs the update on the CPU as well, so the state never moves and the GPU is freed of that work altogether.

The cost is PCIe, at roughly 60 GB/s — far below NVLink and comparable to a network cable. Offload converts a memory problem into a bandwidth problem, and it earns its place only in a run whose binding constraint is GPU memory.

16The two implementations reference

Everything above described an idea. Two pieces of software implement it, and the choice between them is a practical one. ZeRO is the design; DeepSpeed and FSDP2 are two implementations of it with different strengths.

ZeRO stagesoffloadintegration
DeepSpeed1, 2 and 3system memory and storageexternal library, JSON configuration
FSDP23system memorybuilt into PyTorch, composes with the compiler

DeepSpeed is the library Microsoft released alongside the ZeRO paper, configured with a single JSON file naming the stage and the options, with the most complete support for offload. FSDP2 — Fully Sharded Data Parallel, version 2 — is PyTorch's own implementation, shipped as part of the framework and the recommended path from PyTorch 2.6 onward. It corresponds to ZeRO stage 3.

FSDP2 is applied by calling fully_shard() on parts of the model rather than wrapping the whole thing in a class. Each parameter is split along its first dimension and represented as a DTensor — a tensor that knows which part of itself lives on which GPU — which is what lets the compiler work on a sharded model.

Worth naming the overlap with section 06: the engine behind this page is a hand-rolled ZeRO-3 in about 200 lines, and it ran into the same problem FSDP2 solves with storage resizing — a released weight has to stay the same tensor object with a zero-byte storage, because autograd saved that object and will read it again during the backward pass. Finding that out the hard way is most of what I take from this session.

17Precision, and what Blackwell changes computed

Blackwell is the current generation of NVIDIA hardware, following the generation the H100 belongs to. Its arithmetic units can multiply 8-bit floating point numbers directly, which the previous generation could not do at the same granularity. An 8-bit number holds far less detail than a 16-bit one, so it cannot be used naively: the technique that makes it work is to store a shared scale factor alongside a small block of numbers. MXFP8 is the Blackwell-native form, using blocks of 32 values with one shared 8-bit exponent.

Moving the weights and gradients to 8-bit removes two of the sixteen bytes and adds back the per-block scale: one byte for every 32 values, across two tensors, is 0.0625 bytes per parameter. The twelve bytes of master copy and optimizer moments are untouched, because the update arithmetic still needs the accuracy.

This section is computed, not measured, and that is a deliberate line. bfloat16 is as low as this CPU goes, and claiming to have measured MXFP8 on hardware that cannot multiply it would be exactly the thing the rest of this page exists to avoid. The real contribution of 8-bit is elsewhere anyway: matrix multiplication runs faster, activation memory falls, and every multiple of P on this page halves, because P is the parameters in the compute format.

One part of the model is left at higher precision. The attention softmax amplifies small errors in its input, because the exponential turns a modest gap between two scores into a very large ratio. Keeping it in 32-bit costs almost nothing, because softmax is limited by memory bandwidth and not by arithmetic. The operations held at high precision are the operations where high precision is close to free.
