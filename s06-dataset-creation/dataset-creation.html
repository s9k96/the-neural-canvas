Prove What You Trained On

Session 5 produced a mixture plan. Session 6 is the system that executes it and then proves what it did — immutable shards, an evaluation firewall, per-step lane quotas, OPUS with an audit trail, ledgers, and a deliberate crash whose recovery serves a bit-identical batch. Every number on this page was read out of submission_artifacts/.

One command regenerates the whole bundle from a committed corpus snapshot. The assignment's test is not "did it train" — it is can the run prove what it consumed, why it consumed it, what the model learned from it, and how it can be reconstructed.

04Shards, manifests, and the gate

A shard is an immutable training object. Its content hash identifies it, and the shard id embeds the first twelve characters of that hash — so an edited shard is a different shard by name, with its parent recorded. Fourteen manifest fields decide whether it may enter training at all.

Dashed fields are operational additions this implementation needs; the solid ones are the fourteen the session specifies.

Three real rejections

None of these were staged. codeparrot/github-code-clean carries a per-row licence, and one of the rows we fetched is genuinely GPL-2.0 — so the gate refuses the shard containing it. The other two are the firewall's work, below.

05The evaluation firewall

Evaluation data needs manifests too. The difference is permission: training shards are admitted into the stream, test shards are registered precisely so they can be blocked from it, and validation shards sit between — readable during training, never gradient-bearing. Enforcement happens twice: at the gate, and again at serve time, where assert_trainable raises rather than warns.

07Anatomy of one packed batch

This is the object the optimizer actually sees, pulled from the run by rebuilding a recorded batch through the production code path. Two real sequences: one where several samples are packed side by side, and one where the loss mask is doing visible work.

Hover a token.

Why the loss mask is offset by one

Position t predicts token t+1, so loss_mask[t] = is_target(t+1) AND segment(t+1) == segment(t). In the masked example you can watch it flip one token before the answer begins: the last question token bears loss because the thing it predicts is the first answer token. The last position of every segment bears no loss at all — there is nothing in-segment left to predict.

The attention mask, drawn

Causal and same-segment. Padding sees nothing and is seen by nothing. This is what stops two unrelated samples in one window from teaching the model that one is the natural continuation of the other.

08Packing policies, measured

Every unused slot in a window is a token the model did not learn from — but the cheapest packing is not always the safe one. All six policies were run over the same data so the trade-off is a number rather than an assertion.

09OPUS, and why its rejections are kept

Rejection rate by lane — the asymmetry is the design

The proxy is loss-based and the scarce lanes sit behind a protected floor, so they are barely selected against at all. That is the point of the floor: an aggressive selector run on an English-heavy proxy starves native Indic and unfamiliar agentic trajectories toward zero unless they are walled off.

11Crash, resume, replay, fork

Large runs are interrupted. The data system has to define exactly what happens next, and the assignment's hardest test lives here: after recovery, prove the next batch is exactly the expected batch.

Why this is provable at all

Because the planner is a pure function. plan_batch(seed, branch, step) derives everything from the step index plus RNG seeded on (seed, branch, step, lane, slot). No cursor, no generator state, no dataloader RNG survives between steps — so resume, replay and fork are all the same call with the same arguments. "No skipped or repeated batch" stops being something to engineer and becomes something that cannot happen.

Resume — the prediction was written before the crash

Replay — an older interval, reconstructed

Fork — divergence on purpose

Audit — which data trained which interval

14How the evidence checks itself

tds/evidence.py knows nothing about the run. It opens the artifacts off disk and recomputes every claim — shard hashes from shard bytes, lane shares from the ledger, throughput from the effective stream. Crucially it also cross-checks every hash in the three proof files against the consumption ledger, because a proof file that agrees only with itself proves nothing.

The tamper test

Invariant 13 copies the bundle, corrupts one batch_hash in the ledger, and asserts the Replay row flips to FAIL. Try it by hand:

$ python -m tds.evidence submission_artifacts ... edit one batch_hash in ledgers/consumption.jsonl ... [FAIL] Replay failed check: proof_hashes_match_ledger FAIL: 8/9 exit code 1

15Run it yourself

# the complete demonstration, offline and deterministic $ .venv/Scripts/python s06-dataset-creation/run_demo.py # the 13 invariants, against the artifacts it just produced $ .venv/Scripts/python s06-dataset-creation/tests/test_invariants.py # optional: refresh corpus/ from HuggingFace (the only networked step) $ .venv/Scripts/python s06-dataset-creation/prepare_corpus.py

Requires numpy, tokenizers and huggingface_hub. No torch, no datasets, no pytest. Exit code 0 means all nine evidence rows passed.

What the one command produces

From a fresh clone, run_demo.py writes the whole mandated submission_artifacts/ bundle (62 files), the shards/ payloads that sit outside it so manifests can be revalidated against bytes stored elsewhere, and out/s6data.js — the data behind this page. If corpus/ is missing it invokes prepare_corpus.py first and fetches it; otherwise the network is never touched. The page-data build is presentation, not evidence, so a failure there is logged and cannot change the exit code.

corpus/ is the reproducibility anchor. Hashes are byte-stable across runs given the same snapshot; delete it and the re-fetch may legitimately return different rows, so the new artifacts stay internally consistent and still pass 9/9, but their hashes will not match the committed ones.

Checking reproducibility the way a reviewer would

Delete submission_artifacts/, re-run, and compare. Every manifest, ledger, proof and checkpoint array comes back byte-identical. The single exception is the Throughput row of evidence.json, which reports measured rates: its token counts and packing utilization are identical, only the wall-clock-derived rate moves. Checkpoint .npz files are zip archives with embedded timestamps, so compare the arrays inside rather than the file bytes.

16What this deliberately does not do

Two ranks, one process

Rank partitioning is real in the plan and in the ledger — every microbatch records its rank — but there is no distributed loader and no sharded IO across processes.

The mask is honoured, not learned

The model is a linear readout over a masked causal mean, with no learned QK attention. That is enough to make the non-contamination test a real proof, and nothing more is claimed for it.

Long trajectories lose distant context

At a 256-token window, a 2,445-token tool preamble does not fit. Structured samples keep the context nearest their model turn — standard left truncation, and a real limit.

Exact-match dedup only

Session 4 already has the MinHash/LSH near-duplicate pass. This submission records dedup_status from content hashes and does not re-implement it.

Loss delta is first-to-last exposure

Not measured against a held-out probe, so it mixes a shard's own effect with the run's overall progress. Stated in the field name rather than smoothed over.

Every lane reads "covered"

At a 163,840-token budget, of course it does. The verdicts use Session 5's real rule and would flip to repetition-or-synthesis at production scale — which is exactly the argument Session 5 §3 is having.
