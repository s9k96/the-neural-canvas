Words Made of Waves

The Kronecker embedding builds a token's vector by marking a grid of 256 byte values × 32 positions — 8,192 cells, carried whole, with everything past byte 32 thrown away. This page builds the same thing out of waves that add together, and the grid stops being necessary. Every number and every drawing below is computed in your browser from the bytes you type.

01The problem: a bag of bytes has no order

An embedding has to turn a token into one vector. A token is a sequence of bytes, so the real job is to combine which byte with which position into a single object without losing which went with which. That is called binding, and everything else on this page follows from how you do it.

Here is why you cannot skip it. Add the bytes up with no notion of position and the sum forgets the order completely:

02Kronecker binds by building a grid

Make a table 256 rows tall (one per byte value) and 32 columns wide (one per position). For each byte, mark the cell at (its value, its position). That is the outer product, and it is perfectly unambiguous — every (byte, position) pair gets a private cell, so nothing can ever be confused with anything else.

The cost is written into its shape. Type into the box and watch how few cells actually get marked, and how many are carried regardless.

03Fourier binds by rotating a wave

Instead of a grid, give every byte value its own pitch — think of each byte as a tuning fork. A word is what you hear when its tones sound together. One room, however many voices, and the room does not get bigger when more people speak.

A pitch is not a single number — it is a phase at every frequency. The code is a stack of 129 such frequencies, called channels, so a single byte is not one arrow but 129 of them, one per channel. A channel has nothing to do with how long your word is.

Below, each circle is one channel, and inside it each arrow is one byte of your word, drawn tip to tail. Position is how far the arrow is rotated: the byte in slot 0 gets no rotation, slot 1 gets one step, and so on. The thick arrow is their sum. Those sums, across every channel, are the code.

Two dimensions, and they are not the same one. d is the width of this code — frozen, never trained, and the thing every slider on this page moves. d_model (8,096 for V5) is the embedding the transformer actually consumes, and it never changes. One learned Linear(d → d_model) sits between them, so d decides how much survives into that projection and how many parameters it has — d × d_model — not what the model receives.

Only four circles are drawn because 129 will not fit on a screen. Why so many? One channel is a weak identifier — two unrelated words could land on the same resultant by luck. To collide in 129 channels at once is what does not happen, and that is where the code's discriminating power comes from.

It looks like noise, and that is exactly the point: the word's identity is spread thinly across every channel rather than concentrated in a handful of cells. That is what lets a small vector hold a long word — and also what makes section 05 the price.

04Unbinding: asking the code what it contains

Rotating is reversible, and that is the whole trick. To ask “was byte v at position p?” you rotate the sum backwards by that byte-and-position angle and see how far it leans to the right. If that byte really was there, its arrow lands pointing due east and the lean is strong. If it was not, everything stays scattered and the lean is near zero.

Do that for all 256 candidates at every position, take the winner each time, and the byte string falls out. No table is consulted and nothing is stored per token. This is the property the grid does not have, and it is what would let an output head be replaced.

05The catch: everyone is talking at once

You are not getting something for nothing. Circular convolution is a compressed tensor product — it takes that same 8,192-cell grid and folds it down into d dimensions in a way that keeps unbinding approximately possible.

When you tune to one voice you also hear a little leakage from every other voice in the room. Each leak is about 1/√d and there are L of them, so the signal-to-noise ratio goes as √(d/L). Shrink the room or add voices and the transcript starts coming back wrong. Drag both and watch it break.

This is the channels of section 03 seen from the other side. Raising d raises the channel count with it — d=128 listens on 65 pitches, d=2048 on 1,025 — and every extra channel is one more independent measurement of the same superposition, so the leakage averages further down. d is really how many pitches am I listening on.

This is why the two capabilities cost differently. Telling two rooms apart is far easier than transcribing everyone in one, so discrimination works down at d=64 while byte-exact decoding needs d ≈ 20·L.

So is bigger d simply better?

No — only decoding follows √(d/L). Everything an input embedding actually needs saturates almost immediately, and past that point extra d is parameters spent for nothing.

You buy large d for one reason only: you want the code to be invertible, so a decodable vector could stand in for the output head. For an input path, d=64–256 is the whole story. Whether larger d helps training loss is untested here — that needs a real training run.

06The algebra: joining words is adding their codes

Because binding is a convolution, the codec turns concatenation into addition. The code for ab can be built out of the code for a and the code for b — without ever looking at the bytes of ab.

κ(xy)  =  [ √Lx·κ(x)  +  √Ly·rotLx(κ(y)) ]  /  √(Lx+Ly)

What every symbol means

x, y the two pieces being joined. Any byte strings — a character, a syllable, a whole token. In tra+in, x is tra and y is in.
xy the two written together, as one string — train. Not multiplication.
κ( · ) the codec itself: give it a string, it returns that string's code — the d numbers from section 03. κ(x) is x's code.
Lx, Ly how many bytes are in x and in y — not characters. tra is 3 bytes, but भा is 6, because Devanagari costs 3 bytes per character.
rot( · ) the operation. Advances a code by one byte position — a circular convolution with the one fixed position kernel. With the canonical ramp it is literally a circular shift of the waveform.
rotLx( · ) apply rot that many times. y's bytes do not start at position 0 in the joined string — they start after all of x's bytes, so y's code is slid forward by exactly Lx places.
√L factors bookkeeping. Every code already carries a 1/√L scale of its own, so combining means undoing each part's scale and reapplying the joined one, 1/√(Lx+Ly).

Read plainly: take x's wave, take y's wave, slide y's forward by the number of bytes in x, add them, rescale. That is the whole construction — and it is why "represent each character as a wave and add them up" is not a metaphor here.

Two honest footnotes. The identity is exact on the raw code; the shipped codec adds a per-token z-normalisation, which is an affine rescale, so downstream it holds up to that constant. And it only became exact once the DC and Nyquist channels were forced real — with arbitrary phases there, the inverse transform silently discards an imaginary part worth 0.65 at Nyquist and the law misses by about 1e-2. The Kronecker grid has no law of this kind at all: its code is a set of marked cells, so joining two tokens means re-marking the grid from scratch at new positions.

07What it costs, side by side

At V5's reference width (d_model = 8096), the input path is one shared projection from the code into the model. Its size is code_dim × 8096, so code_dim is the entire bill. Kronecker's is forced by arithmetic; the Fourier one is chosen.

Zero collisions across all 63,997 tokens at d = 64 — 128× smaller than the grid it replaces — or full byte-exact invertibility at d = 2048, for the same budget the dynamic Kronecker codec needs just to avoid collisions.

08What it buys, and what it costs

Every line below is a measured number from the run in fourier/submission_artifacts/, not a design intention. The losses are listed at the same weight as the wins, because a compression scheme that only reports its wins is not a result.

What it buys

Dimension stops being forced. Kronecker's 8,192 is arithmetic (256×32). Here d is free, and zero collisions hold down to d=64 — 128× smaller, 518K projection parameters against 66.3M.
Nothing is silently merged. The shipped grid loses 336 tokens on this vocabulary, every one Indic. This codec loses none, at any dimension tested.
No length limit. A 6,144-byte token encodes. There is no window to fall off, so the crop and its collisions cannot occur.
The code is readable back out. 100% byte-exact decode at d=2048; 100% nearest-code retrieval at d=64. Kronecker has no such property, and it is what an output-head replacement would need.
Rare tokens stop being second-class. On tokens never trained on once, a dense table scores 22% against a 20% chance floor; this codec scores 99%. With no rows there are no per-row learning rates for a Zipfian corpus to skew.
Vocabulary size is free. No V appears in the cost. Growing the vocabulary costs nothing on the input side.
Concatenation becomes arithmetic. κ(xy) builds from κ(x) and κ(y) to 2e-15. The grid has no such law.
The capacity law is predictive, not fitted. Measured SNR tracks √(d/L) to within 5.2% across a 16× range, and predicts where decoding collapses.

What it costs

It is lossy where Kronecker is exact. The grid marks L cells with no interference. This superposes waves that leak into each other, so capacity is statistical — good to a probability, not a guarantee.
Separation does not improve with d. 0.982 at d=128, 0.974 at d=2048 — flat. On near-identical strings a tuned dynamic Kronecker reaches 0.964, which is better. This scheme is not strictly dominant.
Byte similarity is arbitrary. Random phases mean a and b get unrelated waves. Parity with Kronecker's one-hot, but the word "wave" invites the hope that similar bytes sound similar, and they do not.
A weaker adapter, by construction. The whole input path is one projection — at d=64, 128× smaller than Kronecker's. Freezing it raises the sustained gradient load on the layers above in every matched pair tested. §9's warning applies here harder, not less.
Codes are dense. The sparse-gather implementations the paper ships, and its compact uint8 byte buffer, do not carry over.
Weight tying is impossible. code_dim ≠ d_model, so there is no transpose to reuse. Costs nothing only because V5 chose an untied head anyway.
A new thing that can silently break a checkpoint. The PRNG seed fixes every wave. Change it and every embedding changes while the tokenizer hash still looks fine — so it has to be pinned in the ledger.
No training-loss claim. Representability, decodability, parameter cost and the rare-token mechanism are measured. Whether any of it converts into better validation loss needs a real training run, and is not claimed here.
The short version. Kronecker pays in space — an exact, sparse grid whose size is forced by its own arithmetic. Fourier pays in noise — a compressed, approximate code whose size you choose. Whether that is a good trade depends on which of the two you have to spend, and on this vocabulary the noise stayed far below the level at which anything measured cared.
