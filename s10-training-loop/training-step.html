One Step, and What It Costs

Session 9 ended holding a single number. This is how that number reaches back and moves every weight — and how you find out, over weeks, whether it is working. Five lines of code, and every serious bug in them is silent. The loss curve is not going to be the one that tells you.

00The five lines

logits = model(batch)        # forward
loss   = loss_fn(logits, y)  # one number
loss.backward()              # fill in every gradient
optimizer.step()             # move every weight
optimizer.zero_grad()        # wipe before the next batch

Every training run in the world is these repeated until the data runs out. Everything below was measured by s10_training_loop.py on a real loop — the same model, the same frozen Sarvam-1 tokenizer and the same S6 corpus as Session 9, because this is literally the next step after that session's scalar.

01A gradient is the answer to a nudge

No calculus needed to start. Take a model with one weight, raise it a very small amount, and see how much the loss moved. That ratio is the most useful number in training: which way, and how urgently. A large value means this weight matters a great deal right now; near zero means the optimiser can leave it alone.

The chain below is the notes' own: h = w₁·x, y = w₂·h, loss = (y − t)². Move the weight, then change how big the nudge is, and watch the slope settle on the same answer from either side.

03Verify one gradient by hand

Nudge a weight, measure how the loss changed, compare against what backward() reported. They should agree to several decimals.

They do — but only if you pick the step size well, and the finite difference is the imprecise one here, not autograd. Too large an h and the chord stops matching the tangent (truncation, ~h²). Too small and subtracting two nearly equal losses destroys the digits you are trying to compare (cancellation, ~ε·|L|/h). Sweeping h shows the U instead of asserting a tolerance.

04The bug that lived in every framework until 2024

Gradient accumulation runs several small batches in turn, lets their gradients pile up, and steps once. The question is how to combine their losses. The correct combination adds up all the loss and divides by all the tokens, so every token carries equal weight. What the frameworks did instead was average the three averages — giving a short micro-batch exactly the same vote as a long one.

Change the token counts below. Make them equal and watch the error drop to zero — which is exactly how this hid for years, because in casual testing micro-batches usually do hold equal counts.

05The grad norm moves first

A single unusual batch can end a run that has gone well for weeks. The guard is a cap: measure the combined size of all the gradients, and when it exceeds a threshold shrink every one by the same factor — leaving the direction untouched and changing only the length.

But the combined figure is worth more than the clipping it enables, because it moves before the loss does. Two traces from one run, sharing an x-axis (never one chart with two scales). The spike arrives in the norm first.

06How a computer holds 0.1

A fixed number of bits must store values as large as 50,000 and as small as 0.00000001 in the same box, so the bits are split three ways: one for the sign, a few for the exponent (how big), and whatever remains for the mantissa (which digits). Every format is a different way of dividing the last two, and the trade is always the same one: exponent bits buy range, mantissa bits buy detail.

0.1 = 1.6 × 2⁻⁴, so every format below stores the same exponent and differs only in how much of 0.6 survives in the mantissa. Each row was decomposed by hand and then checked against the machine.

sign exponent mantissa

0.1 is not representable in binary at any width — it is the repeating fraction 0.0001100110011… — so every row is wrong, and the only question is by how much.

Why bf16 replaced fp16, and it is not accuracy

bf16 keeps all eight of fp32's exponent bits, so it reaches just as far, paying with detail: 7.2 decimal digits down to 2.4. fp16 made the opposite bargain, and that is what breaks it. Late in a run the gradients become genuinely tiny.

07Sixteen bytes for every weight

Running a finished model requires only its weights. Training one requires far more, and this arithmetic is why Sessions 12 and 13 exist.

08MFU, and the number that hides in plain sight

Four traces catch what the others cannot: the loss says whether the model is learning, the grad norm says there is trouble before the loss shows it, tokens/second says whether something quietly got slower, and MFU says whether the machine is being wasted.

The last is the one most often skipped, and the reason to watch it is uncomfortable: at 8% the loss curve looks exactly as it does at 45%. The model learns perfectly well — you simply pay four times as much and wait four times as long, and nothing in the loss will ever mention it.

09The wipe is not optional

Gradients add up rather than replace, so each call to backward() piles the new gradient onto whatever was already there. Forget zero_grad() and batch two trains on top of batch one. That looks like a defect until you remember it is exactly what gradient accumulation relies on — it was built this way on purpose.
